## App 实机流程

所有任务通过原生 App 控件提交，使用 BF16 原始模型、Viggle Turbo v0.3 r256 动态 LoRA（scale 1）、6 节点调度、seed 42、Guidance 1，不开 CFG / step cache。
图像模式的输出设为 512²，以验证流程；条件图仍按官方 1024² 面积预处理。这些数据不用于证明 1024² 性能达标。

| 模式 | 输入 / 操作 | 总耗时 | 实际去噪步数 | 结果 |
|---|---|---:|---:|---|
| 文生图 | 提示词，1024² | 65.37 s | 6 | 完成；非温控数据，稳态约 8.19 s/step，不合格 |
| 参考图创作 | 图库 → 送去创作 → 作为参考图 | 43.33 s | 6 | 完成 |
| 图生图 | 图库 → 送去创作 → 作为初始图，强度 0.6 | 17.74 s | 4 | 完成 |
| 图像编辑 | 主图 + 独立编辑指令，强度 1 | 44.60 s | 6 | 完成 |
| 局部重绘 | 独立大画布手绘蒙版，强度 1，羽化 0 | 51.68 s | 6 | 完成 |

运行中排入后续任务，确认按先后顺序串行执行。切换模式修改参数不会改变已经排入的任务快照。
空编辑指令、空蒙版会禁用生成；文生图提示词与编辑指令分别保存。
大画布实际绘制一笔，撤销后覆盖率为 0，重做恢复 2.6%；关闭大画布回到工作台后笔迹保留。
在最终构建中逐一从五种作品恢复参数，确认模式、提示词、尺寸、种子与 LoRA 恢复；局部重绘另外确认蒙版副本恢复。重启 App 后 Turbo LoRA 仍启用，历史任务与作品保留。

每张结果均核对：任务完成状态、PNG 与 JSON 实际存在、记录的模式/尺寸/seed、完整 LoRA 列表，以及输入副本的 SHA-256。
局部重绘另用当前 `RGBAImage` 解码/缩放逻辑复核：255,340 个未选像素全部 RGBA 逐位相同；6,804 个选中像素中有 6,802 个改变。此项只验证羽化 0 的硬选区保护。

## 本轮修复及测试

蒙版过去只按宽高判断是否需要清空，同尺寸换主图会保留旧笔迹，移除主图也不清理画布。
现在同时绑定主图内容哈希；同一主图保留笔迹及撤销记录，换主图或移除主图清空画布和撤销记录。
作品导出还修复了顶层 `mode` 总是写为 `text-to-image` 的问题；原先 `request.mode` 是正确的，图库依赖后者。现在两处一致，并逐一检查五种模式的 JSON sidecar 与 PNG 内嵌记录。
共 4 项 XCTest 均通过（3 项蒙版测试、1 项遍历五种模式的导出测试）。未新增外部依赖。
生成任务另外补充 `ProcessInfo.beginActivity(.userInitiated)`，以 `defer` 在退出时结束活动；按 [Apple 的长任务活动管理说明](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheAppLevel.html) 避免后台长任务被 App Nap 延后。实机 `pmset -g assertions` 已确认任务中存在 `Generate images` 声明，成功结束后消失；此项没有改善下面记录的 GUI 慢速，不能宣称它修复了性能问题。

## 温控性能

主人本轮明确的标准为不降频时 1024² 文生图 5–6 s/step；如四点采样出现降频信号，允许略高于 6。不能仅凭系统热状态为 nominal 就宣称没有降频。
首次 App 非温控运行约 8.19 s/step；随后测得探针 fair / 9.98 TFLOPS，不能据此证明未降频性能。

`Scripts/benchmark.sh` 现在在去噪前及第 2、4、6 步后记录系统热状态和 BF16 matmul 吞吐。探针放在单步计时外，总耗时包含其开销；探针本身会增加少量 GPU 负载。这是吞吐下降信号，不是直接读取 GPU 时钟。
每轮仍要求 nominal 且连续两次探针 ≥冷机 13.1 TFLOPS 的 98%，间隔 30 秒；正式四点测试期间没有并行编译或 GUI 操作。原始配置保持 100 ops / 200 MB command buffer，不改变 BF16、动态 LoRA、调度或画质。

| 四点测试 | 逐步秒数 | 稳态（第 2–6 步均值） | 0 / 2 / 4 / 6 步探针 TFLOPS |
|---|---|---:|---|
| #1 | 5.94 / 5.95 / 6.02 / 6.04 / 6.06 / 6.10 | 6.035 | 12.910 / 13.020 / 12.724 / 12.618 |
| #2 | 5.99 / 5.95 / 6.01 / 5.98 / 6.07 / 6.07 | 6.016 | 13.125 / 13.026 / 12.704 / 12.639 |

#1 四次系统状态均为 nominal，吞吐峰值到末尾下降约 3.1%，后段单步随之变慢。按本轮补充标准，属于有下降信号时的轻微超出。
#2 四次系统状态同为 nominal，吞吐从首点到末尾下降约 3.7%。两轮稳态均值 6.025 s/step；都没有 Swap 增长（#1 不变，#2 回落 8 MB）。MLX 峰值均约 17.38 GB，进程峰值约 18.12 GB。

保留的前置数据：200 MB 两轮为 6.200（与编译重叠，不能作独立性能结论）、6.124 s/step；256 MB 试验为 6.232 s/step，MLX 峰值从约 17.4 GB 增至 18.3 GB，未采用。

### App 路径复核与观测干扰

App 在探针 13.03 TFLOPS、温控门通过后启动，同配置仍为 7.933 s/step（逐步 7.87 / 7.97 / 7.89 / 7.97 / 7.84 / 7.99），结束后探针为 nominal / 9.18 TFLOPS。
加上长任务活动声明后复测仍为 7.933 s/step；窗口最小化试验为 7.860 s/step。这些自动化观测数据均保留，不把它们改写成通过。
窗口显示/自动采集会干扰系统探针（另开活动监视器后曾下降到 8.78 TFLOPS）。随后主人退出 App，从 Finder 手动重新打开同一构建并生成；本狐只读取任务 JSON，没有再连接窗口或在去噪期间运行探针、编译及其他测试。

手动启动结果：任务 `4EF4AACF-F247-4571-8F96-AD51B0C9DD78`，1024² / 6 步 / seed 42 / Guidance 1 / 同一个 scale 1 的 Turbo LoRA，实际步耗时为 **6.056 / 6.041 / 6.038 / 6.018 / 6.052 / 6.115 s**，稳态 **6.053 s/step**。结束后系统探针 nominal / **13.03 TFLOPS**。这次没有在 App 内插入四点探针，避免重新引入观测负载；四点数据来自上表两轮 CLI。
两轮 CLI 与这次 App 的 RGBA 像素 SHA-256 完全相同：`d3c4a24a92e61cd523d03ea87afd493083078d6de2947b652e7a0902b25750ef`。约 7.9 秒与约 6.05 秒的差异和自动化观测环境有关，不能据此认定推理算法或画质发生变化；没有进一步细分采集、窗口合成及前后台调度各自的贡献。
直接 GPU 时钟采样需要系统权限；`sudo -n powermetrics` 返回需要密码，本轮没有继续提权。

- 本轮模式流程验收使用单个 Turbo LoRA；没有重新进行多 LoRA、40 步标准质量、真 CFG、大批次或多参考图压力测试。

- 量化、step cache、自动语义蒙版等仍不可用；图生图与局部重绘为界面已标注的通用方法。
- 未保存的手绘蒙版不跨 App 重启恢复；已生成作品的记录包含蒙版副本，可从图库复用。
- 交付为本地 ad-hoc 签名 App，不是 Apple 公证安装包。
