# 原生工作台与 Runtime v1 验收

日期：2026-10-18。Runtime 候选为 `runtime-v1-rc1` → `4e1426c`；计算冻结与顺序复验见 [Runtime 报告](runtime-v1-candidate.md)。本报告区分自动回归、实际 GUI 操作与未覆盖边界，不代表全部功能通过。

## 实际发现与修复

| 问题 | 修改 | 验证 |
|---|---|---|
| 左侧内容越过分栏，提示词和参数被右栏遮住 | 将滚动内容约束到实际可用宽度 | 大窗口与约 980×692 紧凑窗口的浅/深色截图均已实际检查 |
| 缺失但已启用的 LoRA 无法关闭 | 允许关闭无效项，阻止重新启用 | 实际移走测试副本后成功停用；自动迁移/刷新回归 |
| LoRA 主列表缺少精度、Rank 与层数 | 保留并展示 inspection 结果；库中添加启用控件 | Turbo BF16、Canon/Samsung FP16 与 Fix 格式的实际列表 |
| 双摄影风格可能相互影响却无提醒 | Canon/Samsung 同时启用时显示非阻断提示 | GUI 仍允许生成；不改用户强度与顺序 |
| 历史恢复模型不完整，可能保留旧初始图/蒙版 | 记录可选模型路径；恢复时清理旧资源，缺失或歧义明确提示 | 独立 profile 的模型、输入、蒙版回归；实际恢复四 LoRA 参考图配方 |
| 输入资源随输出文件夹移动后无法恢复 | 回退到相邻 inputs，并验证完整 SHA-256 | 移动成功、篡改拒绝、缺失提示自动回归 |
| Guidance=1 时丢失用户填写的负面词 | 记录原始负面词，Runtime 仍按原 CFG 条件决定是否计算 | GUI 记录保留，Seed 42 像素仍与候选完全一致 |
| 图片导入失败静默丢弃 | 保留原输入并显示明确错误 | 错误导入与历史缺失输入自动回归 |
| 排队任务输出目录未固定 | 排队时保存目录，旧记录保留兼容回退 | Codable 新旧记录与队列调用检查 |
| 所有多 LoRA 任务共用单 LoRA ETA | ETA 区分实际启用适配器数量 | 计算不变，仅历史估时分类 |
| 运行时旧作品工具栏仍可见 | 生成期间隐藏旧图工具栏 | 真实生成/取消时空画布，无中间预览 |
| 任务列表使用持续旋转图标 | 使用已有回调驱动的确定进度环 | 真实任务界面，无新增轮询 |
| 独立图库不能手动重扫外部变化 | 复用现有 reloadGallery 增加刷新 | 实际打开图库并点击刷新，6 张记录（含 1 张复制基线） |

开发验收使用独立 Bundle ID、独立 `LINGXI_PROFILE_DIRECTORY`、独立 UserDefaults domain 与输出目录，不覆盖主人的图库或偏好。正常 App 不设置此环境变量，使用原存储位置。

## 无窗口接口复测与内存调度实验

关闭所有窗口接口后，用原 GUI 配方再生成：完整新 Swap-out **648.5 MiB**，其中去噪样本 **359.25 MiB**；峰值压缩器 **13.70 GiB**，进程物理 footprint 峰值 **21.69 GiB**，结束约 **250 MiB**。去噪 App CPU 平均约单核 **55.6%**（10 核机器约全机 5.6%），热状态 normal，压力出现 normal/warning。主人反馈稍好但仍有卡顿，所以不将该次系统交互判为通过。输出与缓存未命中、冻结前四 LoRA 基线均逐像素相同。

参考图消融固定原图、提示词、Seed 42、832×1248、CFG 1、完整六步和各 1.0 强度：单 Turbo 既有图与 Turbo+Fix 新图清晰、手鞋结构正常；加入 Canon 后柔化但手脚仍正常；再加入 Samsung 的四 LoRA 图明显发软、手与后脚异常。后者是**不合格的视觉配方**，不能用像素回归通过来宣称画质合格。该结论限这一配方与 Seed，不能推广为 Samsung 单独使用有错误。未自动改用户强度、顺序或停用项。

消融用原 CLI，无窗口接口。两 LoRA 新 Swap-out=0；三 LoRA新 Swap-out=1567.5625 MiB、整机 CPU 均值24.7% / P95 42.6%，其中系统态均值16.3%，热状态正常。没有同时运行本地构建，证明问题不限于 SwiftUI 窗口；仍不能只靠这些计数把所有系统态 CPU 都归到压缩器。

随后只验证 MLX 已有调度水位：20 GiB 软水位下同一完整四 LoRA 参考图逐像素相同、结束 active=0、新 Swap-out=0；去噪 GPU 99–100%、整机 CPU 均值11.2%、App单核37.4%，主人反馈未感到卡顿。峰值压缩器11.95 GiB，仍有短暂 warning。这强烈支持瞬时内存压力/换页是此前主要因素，也说明 GPU 满载本身不足以解释卡顿；不是对所有桌面场景的因果证明。
