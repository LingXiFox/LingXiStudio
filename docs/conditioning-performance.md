# 全精度条件加载、缓存与性能调查

日期：2026-10-18；设备：M5 MacBook Air，32 GB 统一内存。修改前基线为 `0ca7773`。
模型为 Qwen-Image-2.1 BF16，动态 Viggle Turbo r256 LoRA，TF32 关闭。

## 测量方法

- 测试期间关闭窗口共享，不连接 GUI 自动采集；编译、其他模型测试与测速串行执行。
- 每次自动性能测试和真实模型回归前要求 macOS thermal state 为 nominal，且 BF16 4096³ 探针达到冷机 13.1 TFLOPS 的 98%，间隔 30 秒连续两次通过。等待时间不代替吞吐检查。
- 进程资源每 250 ms 采样，阶段内进程物理内存峰值每 20 ms 采样；记录压缩/解压事件、Swap 页计数、进程读写归属和全机 GPU 瞬时利用率。
- 四点热状态、GPU 瞬时利用率不等于实测 GPU MHz。CLI 的四个 BF16 探针位于 prefill 前及第 2/4/6 步后，排除于每步计时，但增加全程耗时与少量热负载。
- 压缩计数是累计处理事件，不能乘页大小后声称为净压缩内存；进程 disk-read 归属不等于物理 SSD 读取。

原始证据保留在 Git 忽略的 `.tmp/conditioning-performance-20261018/`。当前 Metal 录制只启动经过白名单净化环境的 CLI；未附加用户 App，也不导出环境内容。

## Batch 4 / 8 / 16 与逐层加载

同一提示词按 16、4、8、8、4、16 顺序运行，输出 hidden tensor 均为 BF16 `[1,45,4096]`；其字节 SHA256 一致：
`4a5f275054115f5ba5c3e191577c9435c1e844eb70d348feebaf6ba5ee6e91cf`。

| 策略 | 读取/物化耗时（秒） | 编码耗时（秒） | 进程峰值（十进制 GB） | 压缩事件增量 |
|---|---:|---:|---:|---:|
| Batch 16，首轮 | 3.097 | 1.628 | 15.27 | 899,240 |
| Batch 4，两轮 | 2.230 / 2.267 | 0.743 / 0.951 | 15.27 | 456,774 / 478,330 |
| Batch 8，两轮 | 2.251 / 2.246 | 0.947 / 0.977 | 15.27 | 515,800 / 498,191 |
| Batch 16，末轮 | 2.217 | 0.894 | 15.27 | 453,316 |
| 逐层加载，两轮（读取和编码合计） | **1.781 / 0.756** | 已合并 | **1.762 / 1.771** | **0 / 0** |

首轮含 OS 缓存和 JIT 暖机差异，不能据此断言 Batch 4 比 Batch 16 更快。所有 Batch 均保留整套语言权重，无法解决约 15 GB 驻留造成的压缩压力。六轮没有新增 swap-out，只有一轮出现 4 页 swap-in；因此这些样本不支持“加载一定触发大量新 Swap”的判断。

最终实现每层按原 dtype 取出、执行原有公式和 eval 边界，然后移除来源字典引用、同步并释放临时缓存。正负提示词按层分别计算，FP32 residual、BF16 GEMM/Attention、M-RoPE 和 deepstack 保持原逻辑。语言层进程峰值降低约 **88%**；两轮逐层测试均无压缩、swap-in/out 增量，输出张量与原整模实现逐字节一致。每次仍须读取语言权重，只有缓存命中才跳过读取；参考图视觉编码和 DiT 激活的内存不能套用这个纯文本峰值。

证据：`batch-summary.json`、`stream-summary.json` 与逐轮日志/张量。初版 Batch 日志的 `%d` 内存字段发生截断，已修复为 `%lld`，报告采用独立完整宽度采样。早期原始 `cpu_ns` 字段实际为 Mach ticks，汇总按系统 timebase 修正，不能直接把该原始字段当纳秒。

## 无损 Embedding 缓存

- 每个工作线程最多保留当前模型最近一组条件，最多 **128 MiB**；只存独立 CPU Data、shape、dtype、image ranges，不保留 MLX 图或模型。
- 键包括提示词、负面提示词、CFG 分支、模型身份与 tokenizer/config 内容、文本算术设置，以及实际准备后的参考图尺寸、像素、顺序。Seed 不参与键；初始图/蒙版不属于文本条件时不影响键。
- 权重通过 canonical path、device/inode、size、mtime/ctime 纳秒身份检测变更；小配置文件读取内容。缓存命中不重新读取 16 GB 权重。该机制面向正常本地文件更新，不是对主动篡改文件系统元数据的安全认证。
- 模型变化使缓存失效并刷新 tokenizer/scheduler；编码前后身份不一致时报错。超限则正常重算；不跨进程/重启持久化。
- 命中跳过语言与视觉编码，界面显示“复用文本条件”，侧车记录 `conditioningCacheHit`。参考图 VAE 编码和 DiT prefill 仍正常执行。

真实模型测试分别覆盖纯文本和参考图：Seed 42 首次 miss，Seed 43 命中，再用 Seed 43 禁用缓存，后两张 `GeneratedImage.rgba` **逐字节相同**。每张均执行完整 Turbo 6 步；这两项使用 256² 输出检验功能一致性，不作为 1024² 性能数据。参考图实际走约 1 MP 条件预处理。

```bash
swift test -c release --parallel --num-workers 2 --skip HardwareConditioningTests --xunit-output .tmp/tests.xml
LINGXI_RUN_MODEL_TESTS=1 MLX_MAX_OPS_PER_BUFFER=100 MLX_MAX_MB_PER_BUFFER=200 MLX_ENABLE_TF32=0 \
  swift test -c release --skip-build --filter HardwareConditioningTests > .tmp/hardware-model.log 2>&1
```

常规 **16 项通过**，包括跨提示词形状的 DiT 权重释放回归。两项真实模型缓存对照曾分别通过，后续新增内存断言的同进程复验发现纯文本残留约 14 GB，失败记录保留于 `residency-failed/`。最终复验单独记录。SwiftPM 的 parallel xUnit 对 XCTSkip 可能不输出 skipped 节点；串行运行生成的 `*-swift-testing.xml` 只覆盖 Swift Testing，不代表 XCTest 结果，因此真实模型验收依据完整 XCTest 日志及进程退出码，不能把空报告算作通过。

## 去噪与 Metal System Trace

旧记录中约 7 秒/步的任务实际为参考图模式、832×1248、一个条件图；6.053 秒/步的历史任务为 1024² 纯文生图。两者同为约 1 MP，但条件 token 与 attention workload 不同，不能直接据此认定 GUI 变慢。

运行时默认和本次 CLI 日志均确认 **100 ops / 200 MB**，未降低精度、减少生成步数或合并 LoRA 到基础权重。图形后端仍使用既有完整 step compile、QK norm/RoPE 融合和分段前缀 attention，避免退回稠密前缀 mask。

已实际录制 `dit-metal.trace`（Metal System Trace）：完整 32 层、1024² target、31 个 text token、动态 Turbo LoRA，预热后两个 transformer-only step 为 **6.003 / 5.995 秒**。这是随机条件/潜变量的算子诊断，不能当成完整六步出图成绩。

推定连续 DiT 区间 7.538–24.875 秒内，499 个 compute encoder interval 的 GPU 忙碌并集为 17.241 秒，占 **99.45%**；间隙合计 95.97 ms。此区间包含预热及计时迭代，不能把全部间隙简单平均成每步收益。轨迹没有显示扩大 Command Buffer 可带来显著改善的证据，因此保留默认参数。

**测量边界**：该录制的 shader profiler 和 GPU counter 表均为零行，encoder 标签只能定位 Command Buffer，不能分辨每层 BF16 GEMM、Attention、动态 LoRA kernel 的准确时间。GPU performance-state 标签也不是 MHz 或热降频证明。本次未虚构逐 kernel 百分比，未把 encoder 聚合时长冒充每层耗时。源码确认动态 LoRA 仍按原顺序计算 `x Aᵀ Bᵀ` 并叠加；改变加法/归约顺序或烘焙权重不满足本次严格语义约束，不予采用。

四点热状态均为 nominal；吞吐最大下降约 2.5%，有轻微性能下降信号，不能声称频率完全恒定。0.020 秒/步的差异不足以证明去噪回归；三个版本都未复现同工作量下 7 秒/步。首步包含编译/缓存冷热因素，不能把首步差值归因于本次 DiT 加速。

首次新版完整回归暴露了额外的阶段驻留：VAE 开始前仍有约 14 GiB MLX 活跃缓冲，解码进程峰值达 27.48 GB，并伴随新增 swap-out。这次失败保留为 `full-stream.*`，不能纳入通过成绩。首轮补丁在组件边界显式丢弃 compiled step；LoRA 重新绑定使用同一失效入口。该纯文本轮 VAE 开始时 MLX 活跃内存约 0，解码进程峰值恢复到约 13.6 GB，运行结束活跃内存约 0；该轮全程新增 swap-out 为 0。但后续参考图 GUI 仍复现驻留，因此不能把这一次通过视为完整修复。完整任务仍记录压缩与少量 swap-in，不能把语言阶段零压缩推广为整个生成过程零内存压力。

通过证据：`full-baseline.*`、`full-stream-released.*`、对应 `*-summary.json` 与 `full-released-experiment.log`。本轮总耗时 48.2 秒，旧版 54.2 秒；这个差值同时包含首步 JIT/缓存差异，不能当成稳定端到端提速比例。

## 连续生成的生命周期回归

新增真实模型断言要求 VAE 加载前 MLX 活跃内存低于 1 GiB。在同一进程先运行参考图、再运行纯文本各三张的检查中，参考图通过，随后纯文本三张均残留约 14.087 GB 活跃数组，导致 **2 个测试中 1 个失败、3 个断言失败**。该轮缓存像素对照仍一致，但整个验收不能算通过。失败证明仅丢弃 compiled closure、改变 Swift 调用栈和复制输出还不充分；单次 CLI 通过也不能推广到常驻 App。

编译入口原来把基础权重和动态 LoRA 闭包捕获为常量。现在将完整基础参数及按稳定顺序排列的 LoRA 数组显式列为 `compile(inputs:)` 的 state，编译图使用输入占位符而非隐式持有权重常量，并在组件边界丢弃编译函数。数组本身遵循现有 `Updatable` 协议，不新增状态包装器或依赖。这个使用方式由 [MLX Swift 编译文档](https://github.com/ml-explore/mlx-swift/blob/main/Source/MLX/Documentation.docc/Articles/compilation.md) 和本机锁定源码交叉确认；最终同进程实测结果见下文。

前缀临时缓冲采用每层 autorelease pool，并将这段的 MLX 空闲缓存上限限制为 256 MiB，结束后恢复原值；原有 eval 边界、矩阵运算和 attention 分段均未改变。一轮完整参考图对照的峰值从 23.208 GB 降为 21.763 GB、全程新增 swap-out 从 114,352 页降为 0，输出像素仍完全相同。稳态 7.159 秒/步、结束热状态 fair；该单轮不足以断言稳定提速或所有情况下无 Swap，因此保留为内存优化，不宣称去噪达到 6 秒。


显式 state 版本的最终同进程复验 **2 个真实模型测试、零失败，267.842 秒**（包含六次冷机门限与完整六步生成）。每一张都通过 VAE 入口活跃数组低于 1 GiB 的断言；同 Seed 的缓存/重算 RGBA 仍完全一致。额外将全部六张与修改编译输入前的像素逐张比较，也全部相同，记录为 `explicit-state-pixel-parity.json`。完整日志为 `hardware-explicit-state.log`。

`phys_footprint` 的阶段峰值和入口 `Memory.activeMemory` 不是同一个指标：驱动物理回收与 20 ms 峰值采样会跨阶段边界，因此加载 VAE 的窗口仍可能包含此前较高的物理占用；上述断言直接检查入口活跃数组，解码阶段及后续请求也不再维持 14 GB 活跃数组。

证据：`full-final.json`、`full-final.log`、`full-final-summary.json`、`full-final-experiment.log`。

主人完成最终构建的一轮参考图生成，反馈“目前未观察到卡顿”。本轮保持窗口共享和外部资源采样关闭；输出为 `20261018-184813-42`，配置为参考图 832×1248、Seed 42、CFG 1、Turbo 6 步、同一动态 LoRA。稳态 2–6 步为 **6.999595 秒/步**，总耗时 66.168 秒。等待输出的观察器在用户稍后开始生成前已超时，因此较早通过的冷机门限不能证明这次延后运行的温控状态；本轮用于交互和质量验收，不纳入严格温控速度对照。
